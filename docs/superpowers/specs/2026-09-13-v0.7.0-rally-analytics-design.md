# v0.7.0 Rally Analytics Stress-Test Design

**Date:** 2026-09-13  
**Product:** College Athletics Consulting — Volleyball Analytics Platform  
**Base version:** v0.6.6  
**Design status:** Ready for user review before implementation planning

## 1. Objective

v0.7.0 turns the current box-score analytics vertical slice into a deterministic rally analytics engine that works with the evidence VCSU actually has today: public box score/play-by-play pages plus official `vbgame` XML exports from PrestoSports and Volleyball LiveStats.

The purpose of this version is not visual polish. The purpose is to **bend the real VCSU data until the calculations either hold or expose where the evidence is insufficient**. Every new statistic must be traceable to canonical rallies and preserved source evidence. Missing evidence remains missing.

The version must preserve the v0.6.6 production path:

`VCSU program → roster → schedule → canonical matches → evidence → deterministic analytics/findings → Match Summary → Coach's Edge`

v0.7.0 extends that path with canonical sets, rallies, timeline events, rally-state reconstruction, advanced metrics, and source-aware capability gating.

## 2. Product boundaries

### In scope

- VCSU 2026 production data only in the visible product.
- Public website/Sidearm box score **and play-by-play** ingestion when present.
- Official `vbgame` XML ingestion through producer-specific adapters:
  - PrestoSports XML.
  - Volleyball LiveStats In-Arena Tool XML.
- Canonical set/rally timeline persisted in Postgres.
- Score-continuity gap detection and unknown-detail rally placeholders.
- Server/service-state reconstruction.
- Rotation serving-order discovery, recovery, and provisional R1-R6 mapping.
- Sideout, serving, Score1, SOS2, EPO, service-run, and source-supported rally classifications.
- Match Summary exposure of trusted rally analytics.
- Coach's Edge access to persisted deterministic rally metrics/findings.
- Regression fixtures that prove richer sources can be added later without redesigning the canonical model.

### Explicitly out of scope

- GSC/conference statistics, leaderboards, standards, or conference-wide player ingestion. **This old concept is retired.**
- Full multi-program switching. The production model remains one program with historical seasons.
- Final Set Win Probability model math.
- Advantage Index model/calibration.
- Final late-set threshold.
- Rich Contribution fallback-vs-chain attribution rule.
- Production Team Era detection/validation.
- Large visualization rebuilds, heat maps, shot-chart playback, Player Analysis redesign, or old WarhawkVision UI restoration.
- Making VolleyMetrics required for the product to function.

Historical AUM/UWF files may remain in the repository only as isolated regression fixtures. They must never appear in VCSU production data, season totals, Match Summary, or Coach's Edge responses.

## 3. Source architecture

### 3.1 Preserve source family, detect producer

The existing broad source families remain useful for confidence and provenance:

- `public_box_score`
- `official_xml`
- `volleymetrics_xml`
- other existing families

Within `official_xml`, parsing must no longer be monolithic. A producer detector routes `vbgame` files to a producer adapter:

- `presto_vbgame`
- `livestats_vbgame`
- future `genius_vbgame` when activated
- `unknown_vbgame` fail-safe adapter

Producer identity is metadata beneath the broader source family; it does not create a competing analytical model.

### 3.2 Current VCSU fixture set

The supplied VCSU ZIP contains nine official match XMLs:

- 7 PrestoSports files.
- 2 Volleyball LiveStats In-Arena Tool files.

These become the primary v0.7.0 regression corpus.

Known imperfect-source fixtures are intentional acceptance tests:

- Mayville LiveStats contains 195 match points but only 193 explicit scoring records; the two missing scoring rallies must become unknown-detail canonical placeholders.
- The College of Saint Mary Presto file contains a score-continuity jump in Set 3; the missing point must be represented without inventing its terminal event.

### 3.3 Raw-first rule

The import order remains:

`detect → preserve raw bytes → parse → resolve canonical match → reconcile → persist canonical timeline → derive state → calculate metrics/findings`

Raw bytes are preserved before parsing. Re-imports are idempotent. Duplicate bytes may be reparsed by a newer parser version without duplicating the real-world match.

## 4. Canonical event model

The canonical hierarchy is:

`Match → Set → Rally → Offensive Phase → Ordered Event/Contact`

Non-contact timeline events live beside the rally/contact chain rather than pretending to be contacts.

### 4.1 Existing tables retained

- `matches`
- `match_sets`
- `source_artifacts`
- `match_source_links`
- `evidence_observations`
- `canonical_overrides`
- `reconciliation_issues`
- `match_capabilities`
- existing totals, metrics, findings, activity tables

### 4.2 New canonical tables

#### `match_rallies`

One row per real scoring rally, including unknown-detail placeholders.

Required concepts:

- program/match/set identity
- canonical rally ordinal within set
- score before and score after for both sides
- serving and receiving side when known
- point winner
- source-supported terminal event type/player when known
- rally evidence status: `supported`, `gap_placeholder`, `ambiguous`
- canonical revision

A placeholder proves only what score continuity and deterministic rally-scoring rules prove. It may carry a rule-derived serving/receiving **team side** when the previous point winner makes that state certain, but it must not invent the serving player, terminal event, player involvement, attack phase, or attribution.

#### `rally_phases`

Represents an offensive sequence even when that sequence contains no attack.

Concepts:

- rally id
- team side
- `first_ball` or `transition`
- transition depth (`1`, `2`, `3`, ...; null for first-ball)
- phase ordinal
- start/end basis when supported
- confidence/evidence status

This structure is required because freeballs, overpasses, and covered blocks can advance transition depth without creating an attack attempt.

#### `rally_events`

Ordered volleyball events/contacts when the source supports them.

Concepts include:

- rally and optional phase id
- sequence index
- team/player
- event type (`serve`, `receive`, `set`, `attack`, `dig`, `block_touch`, `stuff_block`, `cover`, `freeball`, `overpass`, `ball_over`, etc.)
- outcome
- raw quality grade
- normalized quality value only when a validated mapping exists
- source-specific attack origin/destination/zone fields when present
- timestamp when present
- compact source metadata for non-normalized labels

Basic PBP sources will populate few or no contact rows. Rich sources can populate the same model without changing analytics interfaces.

#### `match_timeline_events`

Non-contact events such as:

- timeout
- substitution
- penalty/administrative point
- challenge/correction
- official rotational adjustment
- starter announcement when useful for state initialization

Timeouts never score and never receive artificial probability impact.

#### `rally_source_links`

Links source-specific scoring/PBP records to canonical rallies and preserves:

- source artifact
- source play/instance key or ordinal
- alignment confidence
- source score transition
- reconciliation status

Ambiguous alignment creates a reconciliation issue instead of forced attachment.

#### Rotation observations/state

Rotation evidence stays distinct by method:

- `coach_confirmed`
- `source_reported`
- `rule_derived`
- `provisional`
- `unknown`

The schema may use a dedicated rotation-state table or an equivalent normalized representation, but it must preserve method, confidence, evidence, and derivation version rather than storing only one unexplained R-number.

## 5. Rally and possession mechanics

### 5.1 Serve and rotation

- A team remains in the same rotation while it continues serving.
- Rotation advances only when the receiving team wins the point and gains serve, except an official correction.
- Substitutions change personnel, not rotational order.
- A player who substitutes into a rotational slot remains bound to that slot under volleyball substitution rules for that set.
- The libero normally does not define a rotation slot; if the libero serves, that serving rotation remains her serving rotation for the set.
- A libero who records a stat/event is known to have participated in that rally only. Participation must not be projected into adjacent rallies without evidence.
- The engine discovers serving order independently for both teams.
- R1 is provisional until coach-confirmed for each set. Confirmation of one set may inform later guesses but never silently locks a later set.
- Once enough of the serving cycle is known, later server observations act as re-synchronization anchors. PBP gaps create local uncertainty, not permanent loss of rotation tracking.
- After the first rally of a set, the canonical serving **team side** is rule-derived from the previous rally winner. Source `serveteam`/server labels are validation evidence, not authority over an impossible serve-state transition. When a source server-team label contradicts the deterministic rally-scoring state, keep the raw source, use the rule-derived team side, and drop the unsupported server-player identity for that rally.

### 5.2 Set rules

Each set resets at 0-0.

- Sets 1-4: first team to at least 25 with a two-point lead.
- Set 5: first team to at least 15 with a two-point lead.
- Extended sets remain valid indefinitely while the two-point rule is not satisfied.

### 5.3 FBSO and transition

Canonical first-ball logic:

- FBSO eligibility exists only for the receiving team.
- FBSO is the receiving team's first offensive sequence after the opponent's serve.
- Only the first attack directly following the serve-receive possession is a first-ball attack.
- A second-contact setter attack can be the FBSO attack.
- A serve-receive overpass that lands for a point is an FBSO kill/attack for the passer.
- An overpass that does not score is not an attack attempt; the FBSO opportunity is over.
- A freeball or other ball-over that ends the first possession ends FBSO eligibility.

Transition depth is **offensive-sequence depth, not attack-attempt count**:

- Serving team's first offensive sequence after defending the receiver is T1.
- Receiving team's first rebuilt offensive sequence after FBSO ends is T1.
- Each new sequence of up to three contacts advances T1 → T2 → T3 → ...
- A freeball or overpass consumes that transition phase even if there is no attack.
- A covered block starts the next transition phase even though the ball never crossed the net.
- A controlled block touch that is kept alive can start a transition possession.

Example:

`FBSO attack → block back → cover → set → attack` = attack in T1.

`T1 attack → block back → cover → set → attack` = attack in T2.

### 5.4 Good Dig

Canonical Good Dig is deterministic:

`Dig → legal second contact/set by any player → actual attack`

A dig that remains playable but ends in a freeball is a dig, not a Good Dig.

### 5.5 Blocking

Keep terminal blocks and controlled touches separate:

- Stuff/terminal block = block point.
- Controlled block touch = no block point; it may create a transition possession.
- Tool = opponent kill off the blocker's hands, not a blocking error.
- Block error = separate technical/statistical category (for example, net violation as coded by source).

Do not credit a controlled block touch with a point simply because the team later wins the rally.

## 6. Rally outcome and attribution model

Do not force all concepts into one enum. Store/derive orthogonal dimensions.

### 6.1 Possession outcome

Examples:

- receiving-side sideout
- serving-side point

### 6.2 Rally pathway when provable

- `first_ball_sideout`
- `regular_sideout`
- `transition_point`
- `direct_serve_point` (ace)
- `unknown_phase`

Opponent service error is treated as an **unearned FBSO** for coaching analysis because the receiving team immediately regains serve without creating the point offensively.

Aces are scored serving points, not transition points.

### 6.3 Earned / Given / Pressure-Created

Retain the locked attribution model:

- `earned`: direct supported scoring action such as kill, ace, terminal block.
- `given`: directly supported opponent giving error such as service error, unblocked attack error, setting error/BHE, or direct-point blocking error.
- `pressure_created`: the opponent records the error but our supported action materially created it, such as block pressure.
- unknown stays unknown.

Headline Earned may combine Earned + Pressure-Created when explicitly labeled.

A blocked attack error is not automatically Given.

## 7. What basic Presto/LiveStats PBP can and cannot prove

v0.7.0 must be aggressive about calculation but conservative about evidence.

### Reliably supported from normal scoring PBP

- rally/set score sequence
- serving side when supplied
- point winner
- service aces/errors
- terminal kills/errors/blocks/setting errors when text supports them
- timeouts when supplied
- starters when supplied
- sideout %
- Point Scored %
- serving runs
- Score1
- SOS2
- EPO where the error classification is supported
- score-state filters
- rotation serving-order reconstruction and resynchronization
- serving-team non-ace wins as transition points
- opponent service errors as unearned FBSO

### Not assumed from terminal PBP alone

A receiving-side non-service-error point is certainly a sideout, but terminal PBP alone often cannot prove whether it was:

- first-ball sideout, or
- a later regular/transition sideout.

When the source does not expose the possession/contact chain, persist `unknown_phase` rather than guessing.

Likewise, basic PBP must not fabricate:

- T1/T2/T3 depth
- Good Dig chains
- contact-quality grades
- attack origin/destination
- exact on-court personnel
- shot charts

Those capabilities unlock only when supported by richer evidence.

## 8. VolleyMetrics enrichment contract

VolleyMetrics is the highest-confidence imported source below staff override. It is **not required for v0.7.0 production success**, but the canonical model must accept it later without redesign.

When present, consistently coded VM fields are authoritative imported observations, including:

- Serve Grade
- Receive Grade
- Set Grade
- Attack Grade
- Dig Grade
- Block Grade
- VM First Ball / Transition phase labels
- reported rotations
- spatial/origin/destination labels
- timestamps

VM First Ball/Transition is authoritative; the deterministic engine independently derives phase as validation and adds T1/T2/T3+ depth.

Historical AUM/UWF VM + Genius files remain test-only fixtures for later enrichment/regression. They never populate VCSU production data.

Passing display scale will eventually be program-configurable between 0-3 and 0-4. Raw grades are preserved. Serving quality remains on the traditional 0-4 display scale. The settings UI for this preference may be deferred until the rich-data wave because VCSU's current sources do not expose the needed contact quality.

## 9. First-wave deterministic metrics

v0.7.0 adds persisted rally metrics only when evidence supports them.

### Team/rally metrics

- Sideout % = receiving-team rally wins / receiving-team opportunities.
- Sideout pathway counts and rates where phase is provable.
- Point Scored % = serving-team rally wins / serve attempts/opportunities.
- Score1 = win first serving rally immediately after sideout; set-ending sideout without subsequent serving rally is censored.
- SOS2 = after sideout, win first serving rally and second serving rally; set-ending before required next rally is censored.
- EPO = after opponent Given error, whether our team wins the immediately following rally; set-ending Given error is censored.
- serving-run length and outcomes.
- score-state splits supported by canonical rally state.
- rotation-level Sideout/Point Scored/Score1/SOS2 when rotation state is supported.

### Transition metrics

For basic PBP:

- serving-team non-ace rally wins may be counted as transition points.
- receiving-side sideouts remain phase-unknown unless the source proves first-ball versus later sideout.

For richer contact evidence later:

- FBSO attack efficiency/kill/error rates.
- transition efficiency by T1/T2/T3+.
- rally-depth performance.
- Good Dig rate.
- offense after controlled block touch.
- quality-grade/context combinations.

The metrics API must return unsupported/unknown rather than zero when capability is absent.

## 11. Reconciliation and gap recovery

### Score continuity

For each set, a valid scoring rally normally increments exactly one side by one point.

If a source jumps by more than one point:

1. Preserve the source row exactly.
2. Create the number of missing canonical rally placeholders required by the scoreboard transition.
3. Mark those placeholders `gap_placeholder`.
4. Populate only provable score-before/score-after/winner information plus rule-derived serving/receiving team side when the previous rally winner makes it certain.
5. Do not invent the serving player, player involvement, terminal event, phase, rotation, or error attribution.
6. Resume normal parsing on the next explicit source record.


### Final-score integrity conflicts

Real source files can contradict themselves. The Mount Mercy Presto fixture does: its official line score says VCSU won Set 1 **27-25**, while the scoring PBP sequence ends **28-24**. Both sequences contain 52 points, so fixing the PBP would require arbitrarily flipping one rally winner.

When a source scoring sequence cannot reconcile to the official set final without changing an explicit rally winner:

1. Preserve the source scoring sequence and source links exactly enough to audit the contradiction.
2. Keep the official line score as the canonical set final in `match_sets`.
3. Mark the set's rally-score integrity as `conflict` and retain the source final score separately.
4. Create/update a `rally_score_conflict` reconciliation issue.
5. Do **not** choose a rally to flip, invent an official adjustment, or silently rewrite the source score path.
6. Withhold match-level rally analytics, sideout-path summaries, and service-run summaries until the conflict is resolved by better evidence or a staff correction. Box-score analytics remain available.

This is a deliberate fail-safe: contradictory evidence is useful evidence, but it is not permission to manufacture a clean rally history.

### Server/rotation recovery

A gap does not invalidate the remainder of a set.

Once the serving cycle is known, a later server observation re-anchors the rotational slot. Uncertain intervals stay uncertain; later supported state becomes known again.

### Cross-source reconciliation

Multiple sources attach beneath one canonical rally timeline. Reconciliation remains field-by-field with staff override first, then source confidence/independent lineage rules. No source silently overwrites conflicting evidence.

## 12. Analytics persistence and versioning

Rally analytics must be versioned separately from source parser versions.

Recommended version concepts:

- parser version per adapter
- rally-state derivation version
- analytics engine version
- canonical match revision

Any import or staff correction that changes canonical rally state increments the match canonical revision and deterministically recalculates affected metrics/findings.

## 13. Match Summary UX for v0.7.0

Do not rebuild the old visual application yet.

Extend the existing Match Summary with a compact **Rally Analytics** section that shows only supported calculations, including:

- Sideout % for both teams.
- Point Scored % for both teams.
- Score1.
- SOS2.
- EPO when supported.
- service-run summary.
- rotation splits when supported.
- a sideout-path breakdown that clearly separates known pathways from phase-unknown sideouts.

Each advanced metric should expose numerator/denominator or opportunity count where useful. Unsupported metrics say `Not available from this evidence` rather than rendering zero.

No large heat maps, shot charts, probability charts, or Player Analysis redesign in this version.

## 14. Coach's Edge UX for v0.7.0

Coach's Edge continues to explain deterministic persisted data only.

Add resolution for supported rally questions such as:

- "What was our sideout percentage against Mayville?"
- "How often did we score the first point after siding out?"
- "How many SOS2 opportunities did we convert?"
- "How long were our best serving runs?"
- "How did we perform by rotation?" only when rotation evidence supports the answer.

For unsupported questions such as exact T3 hitting from a basic Presto match, Coach's Edge must explain that the available source does not contain the contact sequence needed for that calculation.

The known v0.6.6 metric-vs-finding gap remains eligible for correction when touching Coach's Edge routing: metric-specific finding/threshold questions must not be swallowed by a generic metric lookup.

## 15. Stress-test plan

### 15.1 Preserve existing regression suite

All v0.6.6 tests must remain green before new acceptance is considered.

### 15.2 Parse all nine VCSU XML fixtures

Every supplied file must:

- detect the correct producer adapter.
- resolve to the correct canonical VCSU match.
- preserve raw source.
- parse without crash.
- reconcile box-score totals without regressing existing metrics.
- produce a canonical set/rally timeline.

### 15.3 Rally invariants

For every set:

- official `match_sets` final score equals the official line score. A source rally sequence that disagrees is explicitly marked as a score-integrity conflict rather than rewritten.
- each supported rally changes one side's score by exactly one.
- detected gaps create the exact number of placeholders required.
- placeholders do not fabricate unsupported detail.
- total canonical scoring rallies equal total official set points.
- serving/receiving team state follows deterministic rally-scoring continuity where provable; contradictory source server labels do not override it.

### 15.4 Known-gap fixtures

Explicit tests must verify:

- Mayville creates exactly the required missing-rally placeholders and later resumes supported state.
- College of Saint Mary Presto gap is localized rather than corrupting the rest of the set.
- Mount Mercy Set 1 preserves the 28-24 PBP sequence, preserves the official 27-25 line score, records a `rally_score_conflict`, and withholds rally analytics instead of guessing which point is wrong.

### 15.5 Deterministic metric backtests

For each metric, tests calculate expected numerator/denominator from fixture rally state and compare persisted results.

At minimum:

- Sideout %.
- Point Scored %.
- Score1.
- SOS2.
- EPO on fixtures with qualifying errors.
- serving runs.

Existing preliminary Mayville sequence calculations may be used as test hypotheses, but must be independently re-verified from the implemented canonical timeline before being accepted as product truth.

### 15.6 Capability/fail-safe tests

- Basic PBP must not claim transition depth, Good Dig, or contact-quality capabilities.
- Rich fixture parsing later can enable those capabilities without changing canonical interfaces.
- Coach's Edge refuses unsupported slices rather than estimating them.

### 15.7 Production verification loop

After push:

`refresh StackBlitz → npm run verify → npm run dev → import/re-import fixtures → inspect Match Summary → query Coach's Edge`

No acceptance claim is made until the exact live path is tested.

## 16. Migration and compatibility requirements

- Additive Supabase migration only; no destructive rewrite of v0.6.6 tables.
- Existing canonical matches and box-score analytics remain valid.
- RLS/user scoping must cover every new table.
- The browser must not receive service-role access.
- Existing local request serialization/auth behavior remains unchanged unless a failing regression proves a necessary change.
- Generated artifacts (`dist`, `node_modules`, `.core-dist`, `*.tsbuildinfo`) remain out of git.

## 17. Acceptance definition

v0.7.0 is successful when:

1. The nine VCSU official XML files import through producer-specific adapters without corrupting canonical match identity.
2. Canonical set/rally timelines reconcile to official scores when the evidence permits it; irreconcilable source/line-score contradictions are surfaced and gated instead of guessed.
3. Sideout, Point Scored, Score1, SOS2, EPO, serving runs, and supported rotation analytics are deterministic and test-backed.
4. Match Summary exposes the new supported metrics with opportunity counts and honest unavailable states.
5. Coach's Edge answers supported rally questions from persisted metrics and safely refuses unsupported contact-level questions.
6. Re-imports are idempotent and provenance remains traceable to the original source row/artifact.
7. All existing v0.6.6 behavior remains functional.
8. GSC/conference benchmark functionality is absent from the current design and does not influence the data model.

## 18. Deferred next wave

After VCSU production data survives the v0.7.0 stress test, use the historical AUM/UWF VolleyMetrics + Genius pair to enrich the same canonical model with:

- contact sequence
- authoritative VM quality grades
- VM First Ball/Transition validation
- T1/T2/T3+ transition depth
- Good Dig chains
- controlled block-touch offense
- tools/block-quality analysis
- attack origin/destination/routes
- timestamps/video anchors
- shot-chart/heat-map and chronological playback foundations

The richer wave must enrich the platform; it must not become a prerequisite for ordinary VCSU matches.
