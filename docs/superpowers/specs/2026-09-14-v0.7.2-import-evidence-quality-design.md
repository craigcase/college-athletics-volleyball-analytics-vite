# v0.7.2 Import & Evidence Quality — Design Specification

**Project:** College Athletics Consulting — Volleyball Analytics  
**Status:** Approved September 14, 2026; implementation target v0.7.2  
**Date:** September 14, 2026  
**Release target:** v0.7.2  
**Product principles:** FAST. EASY. EFFICIENT. Evidence first. Missing evidence stays missing.

## 1. Purpose

v0.7.2 strengthens the path from imported match evidence to trusted canonical analytics. It preserves the current importer/adapters, then inserts a dedicated evidence/reconciliation layer between source parsing and canonical truth.

This release is intended to solve three real production problems already observed in VCSU testing:

1. legitimate sources can fail to attach because opponent naming differs across schedule, website, and XML;
2. the public Sidearm/Presto page currently exposes more useful evidence than the parser preserves;
3. localized PBP gaps or source disagreements should be reconciled when mathematically provable and otherwise remain localized rather than suppressing unrelated analytics.

The release must not turn data cleaning into the center of the coaching experience. Match-identity ambiguity is resolved immediately. Statistical uncertainty remains visible but non-blocking unless it invalidates a larger structural scope.

## 2. Scope and release boundary

### 2.1 Included in v0.7.2

- Immediate Match Import Review for ambiguous or unmatched sources.
- Program-specific trusted opponent aliases created from authorized confirmation.
- Safe fallback for a match genuinely missing from the schedule.
- Maximum safe extraction from one program-owned public Sidearm match URL.
- Source authority ordering and field-level provenance.
- Box-score/set/player-total cross-checking against PBP.
- Unique mathematical reconciliation when exactly one answer is possible.
- Localized unknowns when reconciliation is not unique.
- Import Quality Summary after every completed import.
- Match-level Data Quality / Reconciliation workspace.
- Guided staff correction for users with data-correction permission.
- Immutable raw evidence, reversible overrides, and audit history.
- Deep Match Timeline / PBP inspection surface, compacted by rally/point and filtered by set.
- Targeted deterministic recalculation after a correction.
- Idempotent re-import and parser-upgrade behavior.

### 2.2 Explicitly deferred to v0.7.3

The following product behavior is already designed and must not be lost, but is intentionally excluded from the v0.7.2 implementation so evidence/reconciliation can be tested independently:

- private coach notes attached to rallies or contacts;
- coach-marked Highlights;
- Save Private / Share with Staff note visibility;
- separate Include in Film Room opt-in;
- private Film Room use that never leaks outside the author’s visibility scope;
- Coach Highlights priority in AI Film Room;
- Coach Highlights section and Match Story integration.

The v0.7.2 data model should avoid blocking these future annotations, but no note/highlight UI or Film Room behavior is required for the v0.7.2 acceptance gate.

### 2.3 Non-goals

- No crawling opponent athletics sites for mirrored match pages.
- No requirement to upload more than one public URL for a match.
- No freeform editing of raw PBP text or source JSON/XML.
- No fabrication of contact chains, attack locations, transition depth, rotations, or player participation that the source does not prove.
- No new AI-calculated statistics.
- No tactical or personnel recommendations.
- No elaborate generic role matrix.

## 3. Architecture

The release uses this pipeline:

**Raw Source Artifact → Source Adapter / Parser → Source Evidence → Match Identity Review → Reconciliation & Evidence Quality → Canonical Match Data → Deterministic Analytics → UI / Coach’s Edge**

### 3.1 Preserve existing import adapters

Existing PrestoSports XML, LiveStats XML, public Sidearm, and future VolleyMetrics adapters remain responsible for fetching and parsing their source formats. They produce observations/evidence; they do not directly define final truth.

### 3.2 Evidence/reconciliation layer

A dedicated layer sits between source observations and canonical values. Its responsibilities are:

- identify the real-world canonical match;
- apply trusted opponent aliases;
- evaluate source authority and lineage;
- compare PBP/event observations to match, set, team, and player totals;
- perform only uniquely solvable reconciliation;
- preserve unresolved detail as unknown;
- apply staff-confirmed overrides;
- record data-quality issues and provenance;
- expose the best defensible canonical fact to analytics.

### 3.3 Source authority

For overlapping facts, authority is:

1. **staff-confirmed override**;
2. **official structured source / richer authoritative source** such as official XML or validated VolleyMetrics evidence for supported fields;
3. **public program website**;
4. **uniquely reconciled derived fact**;
5. **unresolved / unknown**.

Authority is field-specific. One source does not become the blanket winner for every field.

### 3.4 Source lineage

Public Sidearm and an official XML may be two presentations of the same underlying official feed. Preserve both artifacts and provenance, but do not count them as two independent witnesses merely because they agree.

### 3.5 Raw evidence is immutable

Raw artifacts and parsed source observations are never overwritten by a coach correction. Corrections live above source evidence as reversible canonical overrides.

The system must be able to answer:

- what did the source say?
- what did the parser/reconciliation layer conclude?
- what did staff ultimately confirm?

## 4. Match Import Review

### 4.1 Blocking rule

Match identity ambiguity is blocking. An import is not considered complete until the source is attached to the correct canonical match.

Statistical uncertainty after identity is established is not normally blocking.

### 4.2 Automatic path

If match confidence is safely high and there are no material identity conflicts, the source attaches automatically and processing continues with no interruption.

### 4.3 Immediate review path

If confidence is insufficient, immediately show **Match Import Review** rather than quietly leaving the source in an unseen queue.

Show the imported source evidence and best candidate side-by-side. Evidence should include only facts useful for identity:

- source opponent name;
- canonical opponent name;
- date;
- home / away / neutral;
- match result when known;
- set scores when known;
- source match ID when known;
- plain-language explanation of the match evidence.

Primary actions:

- **Confirm Match**
- **Choose Another Match**

### 4.4 Benedictine reference behavior

A source reporting:

- `Benedictine (KS)`
- August 28, 2026
- neutral site
- VCSU 3–1
- 25–16, 21–25, 25–22, 25–22

should be allowed to suggest the existing scheduled Benedictine College match even though the opponent labels are not text-identical.

The system should show why it is suggesting that match; it must not silently expand global normalization rules to make the case pass.

### 4.5 Trusted alias creation

When an authorized user confirms that a source opponent label maps to a canonical opponent, save that label as a **program-specific, opponent-specific trusted alias**.

Example:

`Benedictine (KS)` → canonical Benedictine College identity for this program.

Future imports using the confirmed alias may auto-match. The confirmation remains auditable and can later be revoked/corrected by an authorized user.

Aliases are not global string-replacement rules.

### 4.6 Choose another match

If the suggested match is wrong, allow selection from existing schedule matches for that season. The explicit selection is authoritative for that source attachment.

### 4.7 Match missing from schedule

Do not offer Create New Match as the first response to ambiguity.

After the user reviews existing schedule candidates and confirms none is correct, provide a secondary action:

**This Match Is Missing From the Schedule**

That path may create a new canonical match from source evidence after confirmation. This is deliberately secondary to reduce duplicate-match creation.

## 5. Public Sidearm / Presto maximum safe extraction

### 5.1 Product assumption

V1 assumes one public match URL per match, normally the program’s own athletics-site page. For VCSU testing, that is the VCSU Sidearm page.

The application does not need to discover or crawl the opponent’s mirrored match page.

### 5.2 Extraction principle

**Maximum safe extraction, minimum inference.**

A pasted public match URL should automatically extract every defensible fact the page explicitly supports. The coach should not select individual data categories.

### 5.3 Evidence to preserve when present

- match identity and final result;
- set scores;
- team match totals;
- player match totals;
- set-by-set team attack totals;
- scoring rallies / score progression;
- serving team and server identity when explicit;
- substitutions;
- timeouts;
- set-start / on-court statements;
- hitter / terminal player attribution;
- assists;
- service aces and service errors;
- reception-error attribution when explicit;
- attack errors;
- named block participation;
- block errors;
- setting/bad-set errors;
- other explicit structured terminal-event detail exposed by the page.

### 5.4 Hard evidence ceiling

Sidearm/Presto terminal-event PBP is not a contact-by-contact feed. Do not infer:

- full pass-set-attack-dig chains;
- Good Dig;
- true T1/T2/T3+ depth where possession sequence is not explicit;
- attack origin/destination;
- serve location/type unless explicitly encoded;
- exact six-player on-court state for arbitrary rallies merely from nearby substitutions;
- FBSO vs later sideout when source evidence cannot prove the phase.

Rich contact-level analysis remains capability-gated to stronger evidence such as VolleyMetrics.

### 5.5 Website plus XML

When both public website and official XML exist:

- attach both to the same canonical match;
- use official XML/richer structured evidence for overlapping fields when authority rules are clear;
- let the public page contribute fields not cleanly available from XML;
- preserve both provenance chains;
- never treat mirror agreement as independent-source confidence if lineage is shared.

## 6. Box-score reconciliation and unique derivation

### 6.1 Audit levels

After parsing and match attachment, compare event/PBP evidence against the strongest available totals at these levels when present:

- match team totals;
- set team totals;
- individual player totals.

### 6.2 Three reconciliation statuses

Every audited fact may resolve to:

1. **Directly Verified** — explicitly supported by source evidence and internally consistent.
2. **Uniquely Reconciled** — source detail is missing/ambiguous, but all available constraints leave exactly one mathematically possible answer.
3. **Unresolved** — more than one explanation remains possible.

### 6.3 Unique reconciliation rule

The engine may derive a missing fact only when the constraints admit exactly one answer.

Example:

- PBP accounts for 53 team kills;
- official total is 54;
- exactly one unresolved scoring rally can account for the missing kill;
- all competing terminal categories already reconcile.

The missing terminal classification may be recorded as a reconciled kill, with provenance explicitly marked as derived/reconciled rather than source-reported.

If individual totals also leave exactly one player short one kill and no alternative attribution is possible, player attribution may likewise be uniquely reconciled.

### 6.4 Never solve by plausibility

If two or more explanations remain possible, the engine must leave the fact unresolved. A likely answer is not a proven answer.

A dedicated negative regression test must prove this behavior.

## 7. Localized unknowns and suppression scope

### 7.1 Preserve known dimensions

An unresolved terminal detail does not erase a rally if other rally dimensions are known.

If serving team, receiving team, rally winner, and score progression are known, those fields remain usable even when terminal event or player attribution is unresolved.

### 7.2 Metric-local exclusion

Exclude only the unknown piece from metrics that require it.

Example: a receiving-team rally win with unknown terminal classification can still count toward Sideout %, Score1/SOS2 positioning, score progression, and service-run structure when those inputs are known. It must not be classified as a kill, Given error, Earned point, or player contribution event without supporting evidence.

### 7.3 Smallest defensible suppression scope

When evidence is invalid, suppress the smallest necessary scope in this order:

**field → event/rally → set → match**

Match-level suppression is reserved for structural contradictions that prevent safe use of the underlying sequence, not isolated missing labels.

### 7.4 Structural example

If a set’s PBP score path cannot be reconciled to the official final set score and the missing/contradictory points cannot be localized, set-level rally-derived analytics may be withheld while other sets remain usable.

## 8. Import Quality Summary

### 8.1 Always shown

Every completed import ends with a concise Import Quality Summary, including perfectly clean imports.

### 8.2 Summary content

Use coach-facing language, not raw database diagnostics. Include as applicable:

- canonical match confirmed;
- attached source types;
- data level/capability level;
- rallies processed;
- facts uniquely reconciled;
- unresolved details;
- whether any analytics were suppressed/adjusted;
- entry point to **View Data Quality**.

### 8.3 Example — clean

**Import complete — Benedictine**  
Match confirmed  
Sources: VCSU website + official XML  
Data level: Standard  
181 rallies processed  
No unresolved issues

### 8.4 Example — imperfect

**Import complete — College of Saint Mary**  
176 rallies processed  
2 facts uniquely reconciled  
1 detail remains unresolved  
Affected metrics adjusted automatically  
**View Data Quality**

### 8.5 Blocking behavior

Only unresolved match identity blocks completion. Ordinary statistical gaps remain visible but allow the coach to proceed.

## 9. Data Quality / Reconciliation workspace

### 9.1 Position in product

Data Quality is a secondary match-management surface, not a primary analytics destination.

It should be reachable from:

- Import Quality Summary;
- match details/data-quality indicator;
- a specific unresolved issue link.

### 9.2 Show only actionable or meaningful issues

Do not display every imported field. Focus on issues such as:

- unmatched/ambiguous match identity;
- conflicting source values;
- unresolved rally detail;
- player attribution conflict;
- inconsistent set/match total;
- ambiguous lineup/rotation evidence;
- parser/source structural contradiction.

### 9.3 Issue detail

For each issue show, in plain language:

- original source evidence;
- competing source evidence if any;
- box-score/set/player constraints;
- system conclusion;
- reconciliation status;
- affected analytics/scope;
- link to the affected rally when rally-specific.

### 9.4 Resolved history

Resolved issues move to a **Resolved** history rather than disappearing.

The history must preserve:

- source value(s);
- derived/reconciled value;
- staff-confirmed value if one exists;
- author;
- timestamp;
- optional reason;
- undo/revert events.

## 10. Staff corrections and permissions

### 10.1 Targeted permission

Only Program Owner and Staff explicitly granted **data-correction permission** may:

- confirm match identity when human review is required;
- create/revoke trusted aliases;
- resolve statistical reconciliation issues;
- add staff-confirmed canonical facts;
- undo/revert prior staff overrides;
- restore a fact to best available source-derived truth.

This is a targeted capability, not a broad new role matrix. Player accounts never receive it.

### 10.2 Guided correction UI

Authorized users should not edit raw rows, JSON, XML, or arbitrary database fields.

Use volleyball-specific structured forms appropriate to the issue, such as:

- winning team;
- terminal result;
- relevant player attribution;
- optional supporting detail;
- optional reason.

### 10.3 Optional correction reason

Offer a fast optional dropdown, for example:

- Reviewed film
- Confirmed with official stats
- Scorekeeper correction
- Known roster/player correction
- Other

If Other is selected, allow a short optional note. No reason is mandatory.

### 10.4 Reversibility

Every staff correction can be undone. Undo does not erase history; it restores the next-highest-authority defensible value and records the reversal.

## 11. Deep Match Timeline / PBP inspection

### 11.1 Product position

PBP is a deep inspection/correction tool, not a front-and-center match feature. Coaches should generally work in Match Summary, Players, Rotations, Court, Scouting, and Film Room.

With rich VolleyMetrics evidence, most users may never need to open PBP.

### 11.2 Default presentation

Display a compact chronological list **by point/rally**. Each row should show enough context to identify the point quickly:

- set;
- score after rally or clear score anchor;
- terminal result/primary event when known;
- primary player when known;
- Data Issue indicator when relevant.

### 11.3 Set filter

Pin a set filter at the top:

**All Sets | Set 1 | Set 2 | Set 3 | Set 4 | Set 5**

Only show sets that exist for the match. Default is All Sets.

### 11.4 Additional navigation

Support lightweight filtering/jump behavior such as:

- player;
- Data Issues;
- direct score/set jump when feasible.

Highlight/note filters are deferred until v0.7.3.

### 11.5 Expanded rally record

Expanding a rally shows all evidence available for that point:

- source PBP text/structured observation;
- serving/receiving state;
- rally winner and score transition;
- terminal attribution;
- explicit substitutions/timeouts around the point where relevant;
- canonical/derived classifications;
- source provenance;
- reconciliation status;
- staff override/history;
- rich contact sequence only when an actual rich source supplies it.

### 11.6 Correction entry point

If the rally has a Data Quality issue and the user has permission, the expanded record may expose **Correct / Add Statistical Detail**. The correction remains a structured canonical override; raw imported evidence is never rewritten.

## 12. Deterministic recalculation

### 12.1 Targeted recalculation

A confirmed statistical correction triggers deterministic recalculation for metrics affected by that fact. It does not invoke AI to reinterpret the numbers.

Potentially affected calculations include, depending on the corrected fields:

- Sideout %;
- Point Scored %;
- Score1;
- SOS2;
- EPO;
- service runs;
- Earned/Given/Pressure-Created classification;
- player contribution components;
- affected set/match summaries;
- persisted findings that depend on changed metrics.

### 12.2 Avoid unrelated rewrites

Unrelated sets, players, and metrics should not be changed merely because one rally was corrected. Implementation may recompute a deterministic aggregate from source-of-truth rows for simplicity, but canonical side effects must remain limited to the affected match/program and must not mutate unrelated evidence.

### 12.3 Undo

Undoing an override triggers the same deterministic recalculation using the next-highest-authority evidence.

## 13. Idempotency and parser upgrades

Repeated import of identical evidence must not create:

- duplicate canonical matches;
- duplicate rallies;
- duplicate source artifacts for the same stored artifact identity unless existing storage rules intentionally preserve separate uploads;
- duplicate aliases;
- duplicate active reconciliation issues for the same unresolved fact;
- duplicate staff corrections.

Preserved raw artifacts may be reparsed after parser upgrades. Reparse should enrich/update canonical evidence in place according to authority/provenance rules rather than pretending the source is a new match.

## 14. UI behavior summary

### 14.1 Normal clean path

Paste/upload → auto-match → parse/reconcile → analytics → Import Quality Summary → continue to match.

### 14.2 Ambiguous identity path

Paste/upload → insufficient identity confidence → Match Import Review → Confirm Match / Choose Another → optional trusted alias → parse/reconcile → Import Quality Summary.

### 14.3 Genuine missing-schedule path

Paste/upload → Match Import Review → no listed schedule match is correct → This Match Is Missing From the Schedule → confirm creation → parse/reconcile → Import Quality Summary.

### 14.4 Statistical issue path

Import completes → quality summary reports localized issue → coach can continue immediately → authorized user may later open Data Quality → jump to rally → resolve/override → deterministic recalculation → issue moves to Resolved history.

## 15. Failure behavior

### 15.1 Preserve before interpretation

If raw content is successfully received, preserve it even when later parsing or reconciliation fails.

### 15.2 Plain-language failure states

Distinguish at least:

- fetch failed;
- unsupported/unrecognized source;
- source parsed but match identity unresolved;
- source attached but localized statistical issues remain;
- structural sequence contradiction requires suppression of affected set/match analytics.

### 15.3 No broad failure from local uncertainty

A single unknown attacker or terminal label does not mark the whole match unusable.

## 16. Data model requirements (conceptual)

Implementation should map these requirements onto the current Supabase schema rather than creating parallel systems unnecessarily.

The canonical model needs durable support for:

- source artifacts and source lineage;
- parsed source observations/provenance;
- canonical match/set/rally records;
- trusted opponent aliases with program/opponent scope and confirmation metadata;
- reconciliation issues with active/resolved state and affected scope;
- reconciled/derived fact provenance;
- staff overrides with old/new values, actor, timestamp, optional reason, and reversible status;
- targeted data-correction permission for staff membership;
- import quality summary counts/status derived from persisted evidence;
- stable links from issues to affected rally/set/match.

No implementation should overwrite raw evidence to simulate correction.

## 17. Security and RLS requirements

All new tables/columns must follow the existing authenticated, user/program-scoped Supabase model.

Requirements:

- read access respects current program membership;
- player accounts cannot mutate reconciliation/correction records;
- only users with data-correction permission can confirm/revoke aliases or create/revert statistical overrides;
- server/API checks and database policy should agree; UI hiding alone is insufficient;
- no Supabase secret key is introduced into StackBlitz/local development.

## 18. v0.7.2 acceptance gate

v0.7.2 is not complete until automated verification and guided real-match testing both pass.

### 18.1 Mayville regression

- existing Mayville match remains one canonical match;
- suffix normalization continues to work;
- rally metrics remain intact;
- Coach’s Edge natural-language SOS2 question still resolves to `sos2_percentage`;
- expected Mayville SOS2 result remains 13/47 = 27.7% for VCSU.

### 18.2 Benedictine Match Import Review

Using the official Benedictine XML/public match evidence:

- initial untrusted `Benedictine (KS)` naming mismatch should produce immediate Match Import Review rather than a silent unmatched issue;
- existing scheduled Benedictine match should be suggested from date/neutral/result/set-score evidence;
- user can Confirm Match;
- confirmation attaches evidence to the existing canonical match;
- `Benedictine (KS)` becomes a trusted alias for that canonical opponent;
- a later import using the same alias auto-matches safely;
- no duplicate canonical match is created.

### 18.3 Benedictine extraction audit

Public VCSU URL should preserve all safe Sidearm evidence required by Section 5, including player totals, set totals, substitutions, timeouts, on-court statements, terminal player attribution, and explicit error/block information.

No fabricated contact sequence is allowed.

### 18.4 Benedictine numeric baseline

The canonical match should reconcile to the official 3–1 result and known team totals. Rally analytics should reproduce the independent control values already established for testing:

- VCSU Sideout: 47/86 = 54.7%
- Benedictine Sideout: 46/95 = 48.4%
- VCSU Point Scored: 49/95 = 51.6%
- Benedictine Point Scored: 39/86 = 45.3%
- VCSU Score1: 28/46 = 60.9%
- Benedictine Score1: 22/46 = 47.8%
- VCSU SOS2: 14/46 = 30.4%
- Benedictine SOS2: 10/46 = 21.7%

If implementation discovers a discrepancy between these control values and the locked metric definitions, stop and diagnose the source/engine; do not casually redefine the metric to fit the number.

### 18.5 College of Saint Mary imperfect-PBP case

- known local gap remains localized;
- box-score constraints perform unique reconciliation only when exactly one answer exists;
- non-unique gaps remain unresolved;
- unaffected analytics remain available;
- affected metric opportunities use honest denominators.

### 18.6 Deliberately ambiguous negative case

Create a regression fixture where two terminal explanations satisfy the available totals. The engine must return Unresolved and must not choose one based on plausibility or ordering.

### 18.7 Staff correction and undo

As an authorized user:

- open one test issue;
- apply a guided correction;
- optionally select a reason;
- verify raw source evidence remains unchanged;
- verify canonical value changes;
- verify affected deterministic analytics recalculate;
- undo the correction;
- verify the prior canonical/source-derived result returns;
- verify full history is retained.

### 18.8 Permission negative test

A user without data-correction permission must not be able to create aliases, confirm overrides, or mutate reconciliation facts through either UI or direct API request.

### 18.9 Import Quality Summary

Verify clean, uniquely reconciled, and unresolved imports each produce a concise quality summary and link to Data Quality when relevant.

### 18.10 Idempotency/regression

Repeated imports do not duplicate canonical evidence or aliases. Existing core tests, typecheck, and production build remain green.

## 19. Testing strategy

Automated tests should cover at minimum:

- opponent alias resolution and persistence;
- confidence/review-state transitions;
- Sidearm extraction for richer event types;
- shared-lineage handling;
- direct vs uniquely reconciled vs unresolved classification;
- non-unique reconciliation negative case;
- local suppression rules;
- staff override authority and undo;
- targeted permission checks;
- idempotent re-import;
- Mayville SOS2 regression;
- Benedictine numeric control metrics;
- College of Saint Mary gap recovery;
- Mount Mercy structural contradiction continues to fail safely.

Guided tests remain required because the import/review interaction itself is a product acceptance concern, not only a unit-test concern.

## 20. v0.7.3 locked continuation — coach context / Film Room

This is not part of v0.7.2 implementation, but the following decisions are already approved and should guide schema extensibility:

- coaches may attach notes to rallies/contacts;
- notes are private to the author by default;
- explicit **Share with Staff** never implies player visibility;
- a rally/contact can be marked Highlight without a note;
- Highlight status is separate from AI permission;
- **Include in Film Room** is a separate opt-in;
- private + Film Room eligible can be used only in that coach’s private Film Room experience;
- AI must attribute coach context as coach-provided, not statistically proven;
- Film Room prioritizes eligible coach Highlights above ordinary narrative candidates;
- initial test-drive UI may include a compact Coach Highlights section plus Match Story influence;
- coach annotations never recalculate deterministic volleyball statistics.

## 21. Definition of done

v0.7.2 is done when:

1. ambiguous match identity is resolved in-app immediately and safely;
2. confirmed aliases make future imports faster without broad unsafe name normalization;
3. the program-owned Sidearm page contributes all safe evidence it actually exposes;
4. box-score totals validate and uniquely reconcile PBP only when mathematically conclusive;
5. unresolved detail remains localized and transparent;
6. every import ends with a useful quality summary;
7. authorized staff can inspect, correct, undo, and audit data without mutating raw evidence;
8. the deep PBP view is compact, set-filterable, and useful without becoming a primary navigation surface;
9. all affected analytics remain deterministic and provenance-aware;
10. Mayville, Benedictine, College of Saint Mary, Mount Mercy, automated tests, typecheck, and build all behave according to the locked rules above.
